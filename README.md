# Online Conference

Учебный проект **ПК-01 «Платформа для проведения онлайн-конференций»**. Текущая версия — консольный прототип на Python. В одном терминале можно пройти весь сценарий встречи: войти как администратор, создать организатора, запланировать конференцию, выдать приглашение, подключить гостя и выгрузить отчёт о посещаемости. Прототип моделирует состояния микрофона, камеры и показа экрана.

## 1. Общие сведения

### 1.1 Основание и цель проекта

Основание для разработки — учебное задание по теме «Платформа для проведения онлайн-конференций». В полном проекте организатор готовит встречу для дистанционного занятия, консультации, защиты проекта или совещания. Участники получают приглашение, проходят через зал ожидания, общаются во время встречи, а организатор после завершения получает данные о присутствии.

Цель текущего этапа — проверить правила этого процесса до подключения веб-интерфейса и медиасервера. Например, выдача приглашения и допуск гостя — два отдельных действия. Гость по приглашению может подать заявку, а решение о входе принимает организатор. Разделение видно в терминале и проверяется тестами. Так же проверяются срок действия допуска, права на выступление, занятость показа экрана и расчёт времени присутствия.

### 1.2 Состояние реализации

| Функция | Текущая версия |
| --- | --- |
| Учётные записи | Учебная запись администратора, создание и блокировка организаторов, смена активного пользователя через терминал |
| Планирование | Создание и изменение встречи, список встреч владельца, запуск, отмена и завершение |
| Гостевой доступ | Код приглашения, очередь заявок, решение организатора, вход и временное отключение с возможностью вернуться |
| Работа в комнате | Список подключённых, право выступления, состояния микрофона и камеры, один слот демонстрации экрана |
| Общий чат | Отправка, чтение истории и скрытие сообщения организатором |
| Отчётность | Выгрузка посещаемости завершённой встречи в CSV |
| Хранение | Учётные записи, встречи и сообщения живут в памяти запущенного процесса. Экспортированные CSV сохраняются на диске |
| Веб-версия | По ТЗ планируются браузерный интерфейс, серверный API, постоянное хранилище и передача медиапотоков |

У прототипа один процесс и один активный контекст терминала. Один человек может сыграть несколько ролей, по очереди входя в учётную запись организатора и возвращаясь к гостю по ключу. При этом моделируемые подключения продолжают существовать в памяти до явного выхода, отзыва допуска или завершения встречи. Такая схема позволяет провести демонстрацию на одном компьютере.

### 1.3 Связь с техническим заданием

Техническое задание описывает проект целиком. В нём отдельно заданы архитектура веб-версии, параметры будущего стенда, порядок развёртывания и критерии приёмки. README описывает консольный этап и сценарии, которые можно воспроизвести на коде из репозитория.

Для проверки соответствия текущего этапа используйте сценарий из раздела 4 и тесты из раздела 9. Например, класс комнаты уже ограничивает число участников, но проверка скорости подключения по сети относится к стенду веб-версии. FastAPI, SQLAlchemy, Alembic и Pydantic закреплены в зависимостях для последующих этапов.

## 2. Назначение и роли

| Роль | Как получает доступ | Что может делать |
| --- | --- | --- |
| Администратор | Входит под учебной учётной записью | Создаёт организаторов, блокирует и разблокирует их |
| Организатор | Входит под адресом и паролем, выданными администратором | Создаёт и ведёт свои встречи, выдаёт приглашения, разбирает очередь, управляет выступающими и выгружает отчёт |
| Гость | Подаёт заявку по коду приглашения и указывает имя | Ждёт решения, подключается после допуска, видит состав комнаты и общается в чате |
| Выступающий | Получает право от организатора в активной комнате | Управляет состояниями микрофона и камеры, может занять свободный слот показа экрана |

Право выступления действует в пределах подключения к конкретной комнате. Организатор входит в лимит выступающих и имеет право управлять своими устройствами с начала встречи. Гостю сначала требуется допуск, затем отдельное разрешение от организатора.

Владелец встречи определяется по адресу его учётной записи. Операции с карточкой другого организатора отклоняются. Администратор управляет записями организаторов, а при блокировке приложение закрывает активные встречи этого организатора и отменяет запланированные. Гостевые команды обращаются к комнате из сохранённого гостевого контекста.

## 3. Установка и запуск

### 3.1 Клонирование репозитория

Для новой копии проекта выполните в терминале:

```bash
git clone https://github.com/larlito/Online_Conference.git
cd Online_Conference
```

Если рабочая копия уже есть, выполните из неё:

```bash
git switch main
git pull --ff-only origin main
```

Путь `src/main.py` относительный, поэтому команды запуска выполняются из корня репозитория. Его можно определить по файлам `README.md`, `pyproject.toml` и каталогу `src`.

### 3.2 Запуск на Windows

С установленным Python 3.14 консоль можно запустить через Windows Python Launcher:

```powershell
py -3.14 src/main.py
```

Для Python 3.12 подставьте `-3.12`. Доступные версии можно посмотреть командой `py --list`. Если в вашей системе Python 3.12 или выше доступен как `python`, запустите `python src/main.py`. Для этого варианта достаточно стандартной библиотеки Python.

### 3.3 Запуск через uv

Проект использует Python 3.12 как базовую версию для окружения uv. Зафиксированные зависимости загружаются из `uv.lock`.

```bash
uv sync --locked
uv run --locked python src/main.py
```

При первом запуске программа напечатает приглашение `ПК-01>`. С этого момента вводите команды приложения. `help` показывает список команд, `exit` завершает работу. Если снова виден обычный терминал с приглашением `$` или `PS>`, процесс приложения уже завершён.

### 3.4 Учебная учётная запись

| Поле | Значение |
| --- | --- |
| Логин администратора | `admin@example.test` |
| Пароль администратора | `Admin-demo-2026` |
| Минимальная длина пароля организатора | 12 символов |
| Максимальная длина пароля организатора | 128 символов |

Введите `login admin@example.test`, затем пароль в отдельном приглашении. При вводе пароля символы обычно скрыты. Начальная запись администратора создаётся при запуске приложения. Для демонстрации указывайте тестовые адреса и пароли.

## 4. Сценарий демонстрации

Сценарий рассчитан на один свежий запуск и первую встречу с номером `1`. Если встречи или заявки уже создавались, подставьте номера, показанные вашим терминалом. Команды в блоках этого раздела вводятся **после запуска приложения**, в приглашении `ПК-01>` или в приглашении выбранной роли.

### 4.1 Создать организатора и запланировать встречу

Войдите как администратор и создайте организатора:

```text
login admin@example.test
add-host host@example.test
```

При входе введите пароль администратора, при создании записи задайте пароль организатора. Например, для демонстрации подойдёт `Host-demo-2026`. После создания записи выполните:

```text
login host@example.test
```

Введите пароль организатора. Для встречи выберите время на пять минут вперёд в своём часовом поясе. Укажите явное смещение, например `+03:00` для UTC+3. Подставьте свою дату и время вместо `<дата-и-время>`, угловые скобки уберите:

```text
create "Защита проекта" <дата-и-время> 45 "Демонстрация консольного прототипа"
list
```

Формат времени — `ГГГГ-ММ-ДДTчч:мм+03:00`. Символ `T` отделяет дату от времени. В карточке появятся номер встречи, её состояние и код приглашения. Если опустить описание, карточка сохранится без него.

### 4.2 Запустить встречу и допустить гостя

Находясь в роли организатора, запустите встречу. Затем скопируйте код приглашения из карточки и вставьте его в команду гостя:

```text
meeting start 1
guest <код-приглашения> "Иван Иванов"
```

Вторая команда переключает терминал на гостя. Запомните номер заявки и отдельно скопируйте **гостевой ключ**. Код приглашения служит для новой заявки, а гостевой ключ — для возврата к уже созданной заявке. Теперь снова войдите как организатор:

```text
login host@example.test
queue 1
moderate admit 1 1
```

В команде `moderate` первое число — номер встречи, второе — номер гостевой заявки. После допуска вернитесь к гостю и подключитесь. Уложитесь в 60 секунд с момента допуска.

```text
resume <гостевой-ключ>
join
roster -
```

Прочерк в `roster -` означает текущую комнату гостя. В списке организатор обозначен номером `0`, дальше идут подключённые гости. Если вызвать `join` до решения организатора, приложение сообщит, что нужен действующий допуск.

### 4.3 Проверить чат и права

Из гостевого контекста отправьте сообщение и прочитайте историю:

```text
send - "Презентация готова"
chat -
```

Войдите как организатор и разрешите гостю выступать:

```text
login host@example.test
moderate speaker-on 1 1
```

Вернитесь к тому же гостю и включите состояния микрофона и показа экрана:

```text
resume <гостевой-ключ>
device - mic on
device - screen on
roster -
```

В списке должны измениться признаки микрофона и экрана у гостя. Если организатор уже занял экран командой `device 1 screen on`, попытка гостя начать второй показ завершится ошибкой. Свободный слот можно получить после выключения текущего показа или отзыва права у его владельца.

### 4.4 Переподключение и завершение

Отключите гостя и подключите его снова в течение 60 секунд:

```text
leave
join
chat -
```

История доступна после возвращения. Время между `leave` и повторным `join` не входит в посещаемость. Затем войдите как организатор и завершите встречу:

```text
login host@example.test
meeting finish 1
report 1
exit
```

Итоговый файл находится в `output/attendance_1.csv`. Откройте его после выхода и проверьте строки организатора и гостя. Если вы приняли заявку, но гость ни разу не выполнил `join`, его строки в отчёте не будет.

## 5. Команды терминала

Текст с пробелами заключайте в двойные кавычки. В таблицах заглавные обозначения задают аргументы, например `ID` означает номер встречи. Квадратные скобки обозначают необязательный аргумент и при вводе опускаются.

### 5.1 Вход и управление учётными записями

| Команда | Действие |
| --- | --- |
| `help` | Показать справку по доступному синтаксису |
| `exit` | Завершить текущий процесс |
| `login EMAIL` | Выбрать учётную запись администратора или организатора и ввести пароль |
| `logout` | Сбросить активный контекст терминала |
| `add-host EMAIL` | Создать запись организатора. Доступно администратору |
| `block EMAIL on` | Заблокировать организатора и закрыть его встречи. Доступно администратору |
| `block EMAIL off` | Разблокировать организатора. Закрытые встречи остаются в конечном состоянии |

### 5.2 Встречи и очередь

| Команда | Действие |
| --- | --- |
| `create TITLE DATE MINUTES [DESCRIPTION]` | Создать новую встречу и получить код приглашения |
| `edit ID TITLE DATE MINUTES [DESCRIPTION]` | Обновить тему, время, длительность и описание запланированной встречи |
| `list` | Показать собственные встречи и их состояния |
| `meeting start ID` | Запустить встречу |
| `meeting cancel ID` | Отменить запланированную встречу |
| `meeting finish ID` | Завершить активную встречу |
| `meeting renew ID` | Заменить код приглашения |
| `queue ID` | Показать заявки и их состояния |
| `moderate admit ID GUEST` | Допустить гостя и временно зарезервировать ему место |
| `moderate reject ID GUEST` | Отклонить заявку |
| `moderate kick ID GUEST` | Отозвать действующий допуск и освободить место |
| `moderate speaker-on ID GUEST` | Назначить подключённого гостя выступающим |
| `moderate speaker-off ID GUEST` | Отозвать право выступления и освободить его слот показа |

### 5.3 Гости, устройства и чат

| Команда | Действие |
| --- | --- |
| `guest INVITE NAME` | Подать заявку по коду приглашения и получить гостевой ключ |
| `resume KEY` | Выбрать существующую гостевую заявку по ключу |
| `join` | Подключить текущего гостя по действующему допуску либо вернуть его после временного отключения |
| `leave` | Завершить текущий интервал подключения гостя |
| `roster ID` | Показать список подключённых и состояния устройств |
| `device ID TYPE STATE` | Изменить состояние устройства. Типы: `mic`, `camera`, `screen`. Состояния: `on`, `off` |
| `send ID TEXT` | Добавить сообщение в общий чат |
| `chat ID` | Показать видимые сообщения |
| `hide ID MESSAGE` | Скрыть сообщение по номеру. Доступно организатору |
| `report ID` | Выгрузить CSV по завершённой встрече. Доступно организатору |

В `roster`, `device`, `send` и `chat` организатор указывает номер своей встречи. Гость указывает `-` и работает в выбранной комнате. Чтобы вернуться в терминале от гостя к организатору, используйте `login`; для возврата к уже созданному гостю используйте `resume`.

## 6. Правила работы прототипа

### 6.1 Жизненный цикл встречи

| Состояние | Допустимые действия |
| --- | --- |
| Запланирована | Просмотр, изменение расписания, замена кода, отмена, запуск в разрешённом окне |
| Идёт | Работа с очередью, подключениями, правами и чатом, замена кода и завершение |
| Завершена | Просмотр карточки и выгрузка отчёта |
| Отменена | Просмотр карточки в списке владельца |

При создании и изменении время начала должно находиться в будущем. Окно запуска и приёма заявок открывается за 15 минут до планового начала. Расчётное окончание определяется по плановому времени и длительности. Если приложение обнаруживает, что срок прошёл, активная встреча получает статус завершённой, а запланированная без запуска — отменённой. Эта проверка происходит при обращении к встрече. Интервалы закрываются расчётным временем, если приложение обнаружило окончание позже.

Команда `meeting renew` создаёт новый код. Гость со старым кодом теряет возможность подать новую заявку, а уже созданная заявка сохраняет свой ключ. Закрытая встреча прекращает приём новых заявок.

### 6.2 Заявки и резерв места

1. `guest` создаёт заявку в состоянии «Ожидает».
2. `moderate admit` переводит заявку в состояние «Допущен» и резервирует место на 60 секунд.
3. `join` переводит допущенного гостя в состояние «В комнате» и открывает интервал присутствия.
4. `leave` закрывает текущий интервал и резервирует место ещё на 60 секунд. Если гость успевает вернуться, открывается новый интервал той же заявки.
5. При истечении первичного допуска место освобождается, а заявка возвращается в очередь. При истечении резерва после отключения допуск закрывается, и для нового входа понадобится заявка.

Вместимость — **20 мест с учётом организатора**. Резерв гостя учитывается в лимите до окончания срока. При заполнении комнаты дополнительная заявка остаётся в очереди. Отзыв допуска закрывает соединение гостя и освобождает ресурсы комнаты. Организатор может принять следующую заявку после проверки актуального состояния.

### 6.3 Устройства и чат

У каждой комнаты максимум четыре выступающих вместе с организатором. Включение микрофона и камеры меняет состояние соответствующего пользователя. Слот демонстрации общий: одновременно он принадлежит одному участнику. При отключении, удалении гостя или отзыве права выступления его слот освобождается.

Сообщения получают последовательные номера. В активной комнате чат доступен организатору и подключённым гостям. Организатор может скрыть сообщение по номеру, после чего оно исчезает из общего вывода. Терминальный прототип моделирует управление устройствами и чат внутри процесса. При проверке смотрите на состояния в `roster` и строки в `chat`.

### 6.4 Ограничения ввода

| Поле | Допустимое значение |
| --- | --- |
| Тема встречи | От 3 до 120 символов |
| Описание встречи | До 1000 символов |
| Плановое начало | Дата и время в будущем с явным смещением |
| Длительность | Целое число от 15 до 180 минут |
| Имя гостя | От 2 до 60 символов |
| Текст сообщения | От 1 до 1000 символов |

Для текстовых полей длина проверяется после удаления крайних пробелов. Неподходящее значение вызывает сообщение об ошибке, после чего можно повторить ввод. Пароль организатора проверяется по хешу с индивидуальной солью, вычисляемому через `scrypt`.

### 6.5 Как читать состояния в очереди

| Статус в `queue` | Что происходит | Следующее действие |
| --- | --- | --- |
| Ожидает | Заявка есть, право входа ещё не выдано | Организатор выбирает допуск или отклонение |
| Допущен | За гостем временно закреплено место | Гость выбирает заявку через `resume` и выполняет `join` |
| В комнате | Присутствие учитывается, гостю доступны список комнаты и чат | Гость может выйти, организатор может выдать право выступления или отозвать допуск |
| Связь прервана | Интервал закрыт, место сохраняется в пределах срока переподключения | Гость выполняет `join`, пока срок действует |
| Отклонён | Организатор отказал по этой заявке | Для новой попытки гость подаёт новую заявку по действующему коду |
| Удалён | Организатор отозвал уже выданный допуск | Старый ключ остаётся связан с прежней заявкой, для нового входа нужна новая |
| Доступ закрыт | Резерв переподключения истёк либо встреча закрыта | Проверьте статус встречи. В активную встречу можно запросить новый допуск |

При проверке разницы между резервом и присутствием создайте две заявки. Допустите обоих гостей, выполните `join` только для первого и завершите встречу. В CSV будут организатор и первый гость. Второй гость занимал место в пределах резерва, но интервал присутствия у него так и не открылся.

### 6.6 Как проверяются действия двух организаторов

Создайте две записи организатора через одну административную запись. Войдите под первым адресом и создайте встречу с темой «Консультация». Войдите под вторым адресом и вызовите `list`: встреча первого организатора отсутствует в его списке. Затем выполните `queue` с номером этой встречи. Терминал отклонит запрос к чужой карточке. Войдите под первым адресом ещё раз и убедитесь, что карточка по-прежнему доступна владельцу.


## 7. Отчёт о посещаемости

Команда `report ID` создаёт `output/attendance_ID.csv` в UTF-8. В отчёте присутствуют организатор и гости, у которых зафиксировано хотя бы одно подключение. Отправка заявки и ожидание в очереди временем присутствия не считаются.

| Колонка | Значение |
| --- | --- |
| `participant_id` | Номер участника внутри встречи. Номер организатора — `0` |
| `display_name` | Адрес организатора или отображаемое имя гостя |
| `first_join_at` | Время первого подключения |
| `last_leave_at` | Время выхода из последнего интервала |
| `connected_seconds` | Сумма длительностей завершённых интервалов в целых секундах |

Время выводится в смещении, заданном при планировании встречи. Строки сортируются по первому входу, а при одинаковом времени — по номеру участника. Если имя начинается с `=`, `+`, `-` или `@`, при экспорте перед ним добавляется апостроф, чтобы табличный редактор мог обработать значение как текст.

Пример расчёта: гость пробыл в комнате 30 секунд, отключился на 20 секунд, затем подключился ещё на 10 секунд. В `connected_seconds` попадёт **40**, хотя между первым входом и последним выходом прошло 60 секунд. При повторной выгрузке той же встречи файл обновляется.

## 8. Архитектура и структура проекта

При запуске `src/main.py` собирает три основных объекта. `Accounts` отвечает за учётные записи, `Conferences` управляет коллекцией встреч и гостевых контекстов, а `Console` читает ввод. Когда пользователь отдаёт команду, консоль разбирает её аргументы, определяет роль и вызывает операцию. Правила конкретной комнаты находятся в `Room`. Модуль отчёта получает закрытые интервалы и записывает файл.

### 8.1 Путь команды от терминала до модели

На примере `moderate admit 1 1`:

1. Консоль проверяет количество аргументов и передаёт их обработчику `moderate`.
2. Обработчик проверяет активную учётную запись организатора и запрашивает его встречу с номером `1`.
3. Сервис встреч обновляет временное состояние комнаты и возвращает её владельцу.
4. Комната проверяет состояние заявки и вместимость, затем изменяет состояние гостя и устанавливает срок резерва.
5. Терминал показывает результат. При недопустимой операции пользователь получает сообщение об ошибке и может продолжить работу.

Такой путь можно изучать по отдельности. Например, проверка лимита мест обращается к объектам комнаты и сервиса напрямую, а сквозной тест вызывает те же операции через вводимые команды.

### 8.2 Основные файлы

| Файл | Назначение |
| --- | --- |
| [`src/main.py`](src/main.py) | Точка входа и сборка приложения |
| [`src/accounts.py`](src/accounts.py) | Роли, учётные записи и проверка паролей |
| [`src/cli.py`](src/cli.py) | Справка, синтаксис команд, активный контекст и вывод сообщений |
| [`src/conferences/models.py`](src/conferences/models.py) | Расписание, состояния, гостевые заявки, интервалы и сообщения |
| [`src/conferences/room.py`](src/conferences/room.py) | Правила комнаты, переходы состояний, лимиты, устройства и чат |
| [`src/conferences/service.py`](src/conferences/service.py) | Коллекция встреч, проверка владельца и гостевые ключи |
| [`src/conferences/reports.py`](src/conferences/reports.py) | Расчёт посещаемости и запись CSV |
| [`tests/conftest.py`](tests/conftest.py) | Общие тестовые данные и управляемое время |
| [`tests/test_domain.py`](tests/test_domain.py) | Проверки прав, приглашений, лимитов и окончания встречи |
| [`tests/test_integration.py`](tests/test_integration.py) | Проверки консольного сценария и отчёта |
| [`pyproject.toml`](pyproject.toml), [`uv.lock`](uv.lock) | Описание и фиксация зависимостей, настройки Ruff и pytest |

Часы передаются сервису как функция. В рабочем запуске используется текущее время UTC, а в тестах можно поставить часы на нужный момент и проверить истечение резерва без ожидания минуты. Формирование CSV вынесено из `Room`, чтобы правила допуска не зависели от формата файла. Подробности о разделении обязанностей описаны в [архитектуре](docs/ARCHITECTURE.md).

## 9. Проверка проекта

### 9.1 Автоматические проверки

Из корня репозитория:

```bash
uv sync --locked
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked pytest -q
```

На версии проекта, опубликованной в `main`, прошли семь тестов и обе проверки Ruff. Тесты используют отдельные данные, а тест CSV пишет файл во временную папку.

| Проверка | Ожидаемый результат |
| --- | --- |
| Замена кода | Старый код отклоняет новую заявку. Ранее созданная заявка сохраняется |
| Владение и блокировка | Другой организатор не видит карточку. Блокировка владельца закрывает активную встречу |
| Вместимость | После резерва 19 мест для гостей дополнительный допуск отклоняется. Просроченный резерв освобождает место |
| Выступления и показ экрана | Лишнее право выступления и второй показ отклоняются. Отзыв права освобождает показ |
| Окончание встречи по времени | При позднем обращении интервал организатора закрывается расчётным временем встречи |
| Расчёт CSV | Пауза переподключения исключается. Ожидающий гость отсутствует в выгрузке |
| Сквозной сценарий консоли | Подключение до допуска отклоняется. После допуска работают вход, чат, скрытие сообщения, завершение и выгрузка |

### 9.2 Что проверить вручную

Для обычной проверки пройдите сценарий из раздела 4. Для проверки отказов попробуйте по очереди создать встречу с длительностью 10 минут, отправить заявку по старому приглашению, прочитать чат до подключения и выгрузить отчёт до завершения. После каждой ошибки терминал должен вернуться к вводу команд. Затем повторите операцию с допустимыми данными и проверьте, что сценарий продолжается.

Если команда выглядит зависшей во время входа, проверьте, ожидает ли программа пароль. Если возникает ошибка формата, введите `help` и сверьте порядок аргументов. Если `src/main.py` не найден, вернитесь в каталог с `pyproject.toml` и `src`. При ошибке доступа к комнате сначала проверьте роль, номер встречи и состояние заявки в `queue`.

### 9.3 Проверки перед демонстрацией преподавателю

| Что проверить | Как понять, что всё готово |
| --- | --- |
| Версия проекта | В папке есть `src/main.py`, `src/conferences/room.py`, `README.md` и каталог `tests` |
| Запуск | После запуска появляется `ПК-01>`. Команда `help` показывает и `moderate`, и `report` |
| Смена роли | После `login` приглашение терминала содержит адрес, после `guest` или `resume` — имя гостя |
| Номера | Номер встречи виден в карточке, номер гостя — в выводе `queue`. Их можно подставить в команды вместо демонстрационных единиц |
| Доступ | До `moderate admit` команда `join` отклоняется. После допуска и входа появляется гость в `roster` |
| Итог | После `meeting finish` команда `report` показывает путь к CSV. В файле видны организатор и подключившиеся гости |

Если показываете работу вдвоём, первый участник может показать правила расписания, очереди и допуска. Второй может продолжить с командами чата, устройствами и отчётом. Удобная точка передачи — сразу после входа гостя: в терминале уже видны имена и статусы, а впереди остаются проверки прав и CSV.

Новый запуск создаёт пустой набор встреч. Если во время демонстрации понадобилось начать заново, выйдите через `exit`, запустите программу снова и повторите сценарий с учебной записью администратора. Уже выгруженные CSV остаются в `output/`. Новая первая встреча снова получит номер `1`, поэтому её отчёт может перезаписать старый файл с тем же именем.
