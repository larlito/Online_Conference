# Правила разработки

Работать небольшими изменениями с понятной целью. Перед сдачей запускать `uv run ruff check .`, `uv run ruff format --check .` и `uv run pytest -q`.

## Стиль Python

- Использовать uv и фиксировать зависимости в `uv.lock`. Форматирование и порядок импортов проверять Ruff.
- Называть функции и переменные в snake_case, классы в PascalCase, константы в UPPER_CASE. Для коллекций использовать множественное число, для флагов — имена вроде `is_active` и `has_access`.
- Одинарное подчёркивание обозначает внутренний интерфейс модуля или класса, двойное применяется для действительно приватных деталей. Имена должны описывать смысл.
- Импорты абсолютные относительно корня исходников. Сначала стандартная библиотека, затем зависимости, затем модули проекта. Каждый импортируемый объект на отдельной строке.
- Аннотировать аргументы, возвращаемые значения и коллекции. Вместо `Any` использовать конкретный тип или типизированный контракт.
- Описывать назначение классов и функций в docstring сразу после объявления. Пояснять контракт и важные ограничения. Комментарии внутри алгоритмов не дублируют действия кода.
- Избегать вложенных функций, динамического изменения классов и множественного наследования собственных классов с состоянием. Фабрики приложения, маршрутные функции и управляемые зависимости оставлять простыми. Использовать композицию и явные зависимости.

## Границы приложения

- Проектировать схему в ER-диаграмме и менять её миграциями Alembic. Использовать `Mapped`, `mapped_column`, явные ключи и парные `relationship(..., back_populates=...)`.
- SQL выполнять через репозитории. Бизнес-правила хранить в модели и Service Layer. Транзакцию открывать и завершать через `Session.begin()`.
- Группировать HTTP-операции по ресурсам в `APIRouter`. DTO хранить отдельно от ORM. Документировать ограничения, примеры и ошибки в OpenAPI.
- Проверять прототип и API через изолированные тесты. Использовать временное хранилище, управляемые часы и подмену внешних зависимостей.
